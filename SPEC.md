## 1. Управление клиентами

Реализовать возможность добавлять, просматривать, редактировать и удалять получателей
рассылки (клиентов).

Модель «Получатель рассылки»:
- Email (строка, уникальное)
- Ф. И. О. (строка)
- Комментарий (текст)

## 2. Управление сообщениями

Реализовать возможность добавлять, просматривать, редактировать и удалять сообщения.

Модель «Сообщение»:
- Тема письма (строка)
- Тело письма (текст)

## 3. Управление рассылками

Реализовать возможность добавлять, просматривать, редактировать и удалять рассылки.

Статусы рассылки:
- **Создана** — рассылка была создана, но ещё ни разу не была отправлена
- **Запущена** — рассылка активна и была отправлена хотя бы один раз
- **Завершена** — время окончания отправки рассылки прошло

Модель «Рассылка»:
- Дата и время первой отправки (datetime)
- Дата и время окончания отправки (datetime)
- Статус (строка: 'Завершена', 'Создана', 'Запущена')
- Сообщение (внешний ключ на модель «Сообщение»)
- Получатели («многие ко многим», связь с моделью «Получатель»)

## 4. Отправка сообщений по требованию

Реализовать возможность отправки рассылки вручную через интерфейс пользователя
и командную строку.

## 5. Попытки рассылок

Для каждой попытки отправки рассылки должны сохраняться: дата и время попытки,
статус (успешно / не успешно), ответ почтового сервера.

**Логика работы попытки рассылки**

1. *Инициация отправки.* Попытка рассылки создаётся каждый раз, когда запускается
   процесс отправки сообщений для конкретной рассылки.
2. *Определение получателей.* Список клиентов определяется из выбранных клиентов
   для данной рассылки.
3. *Отправка сообщения.* Для каждого клиента из списка выполняется отправка письма
   с помощью функции `send_mail()` из Django. При успехе создаётся запись в модели
   «Попытка рассылки» со статусом «успешно». При ошибке (например, почтовый сервер
   недоступен) — запись со статусом «не успешно» и текстом ошибки в поле
   «Ответ почтового сервера».
4. *Сбор статистики.* Каждая попытка отправки письма фиксируется — видно успешные,
   неуспешные и общее количество попыток.
5. *Анализ и отчётность.* Данные о попытках используются для статистики и отчётности
   о статусе и результатах рассылок.

Модель «Попытка рассылки»:
- Дата и время попытки (datetime)
- Статус (строка: 'Успешно', 'Не успешно')
- Ответ почтового сервера (текст)
- Рассылка (внешний ключ на модель «Рассылка»)

## 6. Главная страница

Отображается количество всех рассылок, количество активных рассылок (со статусом
'Запущена') и количество уникальных получателей.

## Решения по спорным местам

Ответы владельца/куратора на вопросы, которых сам текст ТЗ не закрывает. Здесь —
источник истины для схемы, в `TODO.md` — что из этого осталось сделать.

**Q1 — пользователи и вход (28.09.2026).** Авторизация нужна, но откладывается.
Модель `users.User(AbstractUser)` заведена до первой миграции, `AUTH_USER_MODEL`
зафиксирован; формы входа и регистрации делаются позже. Открыто: появится ли владелец
(FK на пользователя) у получателей, сообщений и рассылок — решать до блока 2.

**Q2 — сколько попыток создаётся (28.09.2026).** Дословно: «сначала создаёте попытку на
запуск, а затем для каждого клиента в этой рассылке создаётся отдельная попытка,
отражающая результат отправки конкретного письма. Это позволяет более детально
анализировать успешность и неуспешность рассылок, а также получать статистику по каждой
отправке».

Следствия для схемы (отступления от буквы ТЗ, сделанные ради этого ответа):
- у «Попытки» появляется **`client`** — FK на получателя, `null=True`: пусто у записи
  о запуске, заполнено у записи о конкретном письме. Без него «статистика по каждой
  отправке» нечитаема: видно, что письмо не ушло, но не видно кому;
- у «Попытки» появляется **`parent`** — FK на саму себя, `null=True`: письмо ссылается
  на свой запуск. Иначе письма одного запуска приходится группировать по времени;
- статус записи о запуске проставляется **по итогу прохода**, а в «Ответ почтового
  сервера» у неё пишется сводка (сколько ушло, сколько упало), потому что в момент
  старта результат ещё не известен.

**Q3 — кто переводит рассылку в «Завершена» (28.09.2026).** Дословно: «статус рассылки
переводится в "Завершена" автоматически системой на основе времени окончания отправки,
которое было задано при создании рассылки. Как только текущее время превышает это заданное
время окончания, статус рассылки нужно обновить на "Завершена". Это может быть реализовано
в виде фоновой задачи, которая периодически проверяет и обновляет статусы рассылок в базе».

Следствия:
- логика перехода живёт **в одном месте** — методе менеджера/QuerySet
  (`Mailing.objects.finish_expired()`): один `UPDATE` по всем просроченным,
  а не цикл с `save()` по объектам;
- «фоновая задача» = команда `manage.py update_mailing_statuses`, которую вешают
  на планировщик ОС (Планировщик заданий Windows или cron). Отдельная библиотека
  (`django-apscheduler`) не нужна: её можно добавить позже, не меняя саму логику;
- между запусками задачи хранимый статус **врёт** — на главной рассылка с истёкшим
  временем ещё числится «Запущена». Поэтому тот же метод вызывается перед подсчётом
  статистики и перед отправкой, иначе цифры и письма расходятся с реальностью;
- переход «Создана» → «Завершена» законен: время вышло, а рассылку так и не запустили.

**Владелец у клиентов, сообщений и рассылок (28.09.2026).** Ответ куратора: в ТЗ такой
связи нет, но она нужна, если планируется ограничение доступа «каждый управляет только
своими данными», и тогда в три модели добавляется FK на пользователя.

Решение: **поле добавляем сразу**, `owner = ForeignKey(settings.AUTH_USER_MODEL,
null=True, blank=True, on_delete=models.CASCADE)` в `Client`, `Message` и `Mailing`.
Авторизация отложена (Q1), поэтому поле пока пустое; когда появится вход, оно
заполняется во `form_valid()` из `self.request.user`, а списки фильтруются по нему.
Добавить потом — это три миграции по живым данным, добавить сейчас — три строки.

⚠️ Пример в ответе куратора приведён в псевдокоде, и дословно его переносить нельзя:
- `from django.contrib.auth.models import User` + FK на `User` — **у нас так не будет**:
  проект живёт на своей модели (`AUTH_USER_MODEL = 'users.User'`), ссылаться нужно на
  `settings.AUTH_USER_MODEL`. Прямая ссылка на встроенного `User` при своей модели —
  это ошибка системных проверок Django, а не стилистическая придирка;
- имена полей и классов — латиницей (`Client`, `owner`, `full_name`), русский текст живёт
  в `verbose_name`. Кириллица в именах полей ломает формы, admin и адреса;
- `on_delete=CASCADE` у владельца означает: удалили пользователя — вместе с ним исчезли
  его клиенты, сообщения и рассылки. Для учебного проекта берём как в примере, но знать
  об этом надо; альтернатива — `PROTECT`.

**Q5 — база данных (29.09.2026).** Стек на **PostgreSQL**, SQLite не используем.

Следствия:
- зависимость `psycopg[binary]`, `ENGINE` = `django.db.backends.postgresql`;
- параметры подключения (`DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`) —
  из `.env`, с прописанными ключами в `.env.example`. В коде ни пароля, ни имени базы;
- базу на машине надо создать руками, миграции применить заново — они
  БД-независимы, переносить ничего не нужно;
- `db.sqlite3` после переключения не используется; удалять его руками и осознанно —
  в нём остаются данные ручных проверок;
- проект перестаёт подниматься «из коробки» у того, у кого нет PostgreSQL, — README
  должен это прямо говорить.

**Q4 — «уникальные получатели» на главной (29.09.2026). Допущение, куратор не отвечал.**

«все клиенты в базе» слово «уникальных» в ТЗ было бы лишним. Если куратор скажет иначе —
правка одной строки в `home_stats()` (`mailings/statistics.py`).
